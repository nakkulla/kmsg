# 시간 기준 전체 읽기(`--since`)와 안 읽음 숫자 설계

**날짜:** 2026-11-19
**상태:** 초안 — 사용자 검토 전
**레포:** `nakkulla/kmsg` (channprj/kmsg fork)

## 목적

아침 브리핑이 단톡방을 요약하려면 두 가지가 필요하다.

1. 방마다 안 읽은 메시지가 몇 개인지 안다.
2. 정해진 시각 이후에 온 메시지를 개수 제한 없이 전부 읽는다.

기준은 사용자가 정한 대로 "둘 다"다. 안 읽음 숫자는 보여 주기만 하고, 메시지는 시간 기준으로 가져온다. 시간 기준은 휴대폰에서 먼저 읽어도 빠지지 않고, kmsg가 방을 열어 읽음 처리가 되어도 결과가 달라지지 않는다.

## 확인한 사실

2026-11-19에 "94즈" 단톡방에서 직접 쟀다. 보내기는 하지 않았고 읽기만 했다.

- 처음 열면 대화창 표(AXTable)에는 약 50줄만 올라와 있다. `--limit 1000`으로 읽어도 48개만 나오고, 28초가 걸렸다.
- 세로 스크롤바 값(`AXValue`)을 0으로 바꾸면 카톡이 예전 메시지를 약 50줄씩 더 불러온다. 한 번에 2초쯤 걸리고, 줄 수는 52 → 106 → 156 → 207 → 257 → 307로 늘었다.
- 불러온 줄은 사라지지 않고 쌓인다. 307줄 중 298줄에 글자가 들어 있었다. 화면 밖 줄도 비어 있지 않다.
- 위로 올린 상태에서 읽으면 65개(11-10)만 나온다. `collectTranscriptRows`가 입력창보다 아래에 있는 줄을 버리기 때문이다(`TranscriptReader.swift:216-220`).
- 맨 위까지 불러온 뒤 스크롤바를 1(맨 아래)로 되돌리고 읽으면 286개(11-10 오후 1:32 ~ 11-19)가 모두 나온다. 다만 117초가 걸렸다. 줄마다 AX 요청을 여러 번 보내는 분석 단계가 느리다.
- 메시지마다 `date`(YYYY-MM-DD, 시각 라벨의 AXHelp)와 `time_raw`("오전 10:34")가 빠짐없이 있었다.
- 채팅 목록의 안 읽음 배지는 `identifier == "Count Label"`인 정적 텍스트다. 지금은 제목 후보에서 걸러 내기만 한다(`ChatListScanner.swift:241`, `:263`).
- MCP `kmsg_read`는 `limit`을 입력 규칙과 코드 양쪽에서 100으로 자른다(`MCPServerCommand.swift:312`, `:478`). 자식 프로세스 제한 시간은 8초, deep recovery에서는 15초다(`:506`).

## 설계

### 1. `kmsg chats`의 안 읽음 숫자

- `ChatListEntry`에 `unreadCount: Int?`(JSON `unread_count`)를 더한다. 배지가 없으면 `null`, 있으면 숫자다. "999+" 같은 값은 `+`를 떼고 숫자만 남기며, 넘친 표시를 위해 `unread_count_capped: true`를 둔다.
- 행을 훑을 때 `Count Label` 요소의 값을 읽어 둔다. 제목·미리보기 후보에서 걸러 내는 기존 동작은 그대로 둔다.
- 사람이 읽는 출력에는 제목 뒤에 `(N)`을 붙인다.
- 방을 열기 전에 목록에서 숫자를 읽으므로, 열면서 읽음 처리되더라도 숫자는 남는다.

### 2. `kmsg read --since <시각>`

- `--since`는 ISO 8601 시각(`2026-11-18T07:00:00+09:00`)이나 상대값(`24h`, `90m`, `2d`)을 받는다. 시간대가 없으면 로컬 시간으로 본다.
- 메시지 시각은 `date` + `time_raw`(오전/오후 h:mm)로 로컬 `Date`를 만든다. 같은 분 안의 순서는 화면 순서를 따른다.
- 불러오기 반복(page-up):
  1. 대화창을 연다(기존 해석·열기 경로 그대로).
  2. 지금 올라온 줄 가운데 가장 오래된 줄의 시각만 가볍게 읽는다. 시각 라벨만 보고 본문 분석은 하지 않는다.
  3. 그 시각이 `since`보다 늦고 스크롤바가 0보다 크면, 스크롤바를 0으로 바꾸고 줄 수가 늘 때까지 기다린다(최대 3초).
  4. 가장 오래된 줄이 `since`보다 이르거나, 줄 수가 더 늘지 않거나(대화 시작), 상한에 닿으면 멈춘다. 상한은 `--max-pages` 기본 40쪽(약 2000줄)과 전체 제한 시간이다.
  5. 스크롤바를 1로 되돌린 뒤 읽는다. 입력창 아래 줄을 버리는 기존 규칙과 충돌하지 않는다.
- 분석은 가장 최근 줄부터 거꾸로 하다가 `since`보다 이른 메시지를 만나면 멈춘다. 117초 중 대부분이 줄 분석이므로, 필요한 줄만 분석해 시간을 줄인다.
- 출력은 `since` 이후 메시지 전부를 시간 순서로 낸다. `--since`를 쓰면 `--limit`은 안전 상한으로만 쓴다(기본 2000).
- JSON에는 `since`와 `oldest_reached`(대화 시작까지 닿았는지), `truncated`(쪽·시간 상한에서 멈췄는지), `pages_loaded`를 더한다.
- 읽은 뒤에는 스크롤을 맨 아래로 두고, 잠깐 연 창은 기존처럼 닫는다.

### 3. MCP

- `kmsg_read` 입력에 `since`(string)를 더한다. `since`가 있으면 `limit` 상한은 2000, 기본은 2000이다. 없으면 지금처럼 최대 100, 기본 20이다.
- `since` 읽기의 자식 프로세스 제한 시간은 `timeout_sec` 입력(기본 180초, 최대 600초)으로 정한다. 쪽 수가 많으면 2분을 넘길 수 있다.
- 결과 `meta`에 `since`, `oldest_reached`, `truncated`, `pages_loaded`를 싣는다.
- `kmsg_chats` 결과는 `unread_count`를 그대로 전달한다. 설계 당시 MCP에는 `kmsg_chats` 도구가 없었으므로, 이 브랜치에서 읽기 전용 `kmsg_chats` 도구(`kmsg chats --json` 실행, 입력 `limit`·`keep_window`·`trace_ax`, 제한 시간 20초)를 새로 더했다.

### 4. 문서와 시험

- `README.md`, `README.en.md`, `USAGE.md`, `skills/kmsg/SKILL.md`에 `--since`와 `unread_count`를 적는다.
- `tests/`의 Python 계약 시험이 MCP 입력 규칙(최대 100)을 고정하고 있으면, `since`가 있을 때의 규칙을 함께 고정하도록 고친다.
- 순수 함수(상대 시각 해석, `date`+`time_raw` → `Date`, 배지 문자열 → 숫자)는 Swift 시험 대상으로 만들고 싶지만 지금 Package에 test target이 없다. 이번에는 Python 계약 시험과 수동 확인으로 두고, test target 추가는 따로 묻는다.

## 검증

- `swift build -c release` 성공.
- `python3 -m pytest tests -q` 통과(레포의 실행 방법을 따른다).
- 수동 확인, 사용자 허락 범위의 "94즈" 방에서 읽기만:
  - `kmsg chats --json`에 `unread_count`가 나온다.
  - `kmsg read --chat-id <94즈> --since 2026-11-10T00:00:00+09:00 --json`이 11-10 이후 메시지를 모두 내고, `oldest_reached`와 `truncated` 값이 맞다.
  - `--since 24h`가 마지막 24시간만 낸다.
  - 걸린 시간을 기록하고, 위 117초보다 짧아야 한다.

## 덧붙임 (2026-11-19, 같은 브랜치)

- 창 화면 밖 배치: `kmsg read --layout offscreen`은 대화창을 연 직후 크기는 그대로 두고 모든 디스플레이 합집합의 왼쪽(x = 합집합 minX − 창 너비 − 100, y는 그대로)으로 옮긴다. macOS가 위치를 잘라도 받아들인다. 컨트롤러 실측에서 화면 밖에서도 스크롤바 불러오기와 읽기가 그대로 됐다. 원래 열려 있던 창(또는 `--keep-window`)은 끝날 때 원래 위치로 되돌리고, kmsg가 연 창은 기존처럼 닫는다. `--background-safe`에서는 옮기지 않는다. MCP `kmsg_read`의 `layout`도 `offscreen`을 받고, 기본값은 `KMSG_DEFAULT_READ_LAYOUT`, 없으면 `KMSG_DEFAULT_LAYOUT` 환경 변수에서 읽는다.
- 검색어 남김 수정: 채팅방을 찾으려고 메인 창 검색칸에 이름을 입력한 뒤(읽기·보내기·이미지 보내기·watch가 함께 쓰는 검색 경로와 `cache warmup`) 끝날 때 오류가 나도 검색칸을 원래대로 돌린다. kmsg가 입력한 이름이면 지우기 버튼을 누르고 값을 비우며, 원래 사용자가 적어 둔 글이 있었으면 그 글로 돌린다. 그사이 다른 글로 바뀌었으면 건드리지 않는다. 이 버그는 upstream Homebrew 빌드에도 있었고, 남은 검색어 때문에 뒤이은 `kmsg chats`가 걸러진 방만 보였다.

## 열린 질문

- 맨 위까지 불러올 때 2초 대기를 줄 수 증가 감지로 대신해도 카톡이 안정적으로 따라오는지.
- 방을 열면 카톡이 그 방을 읽음 처리하는지. 이번 측정에서는 따로 확인하지 않았다.
